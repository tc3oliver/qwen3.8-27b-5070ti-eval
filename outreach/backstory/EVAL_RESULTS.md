# 模型能力評測紀錄

用 `tests/test_model_eval.py` 的 10 題跑分，評分標準統一如下（每題 10 分）：

- **10**：完全正確，無虛構，嚴格遵循要求
- **7**：核心正確，但有少量格式或表達問題
- **4**：部分正確，有明顯遺漏或自行推測
- **0**：錯誤、編造或違反核心指令

每次測新模型，把該模型的啟動參數（`-c`、`temp`、`top-p`、`top-k`、`repeat-penalty` 等）記錄清楚，因為這些會直接影響分數，不同參數下的分數不完全可比。

## MTP 推測解碼基準（2026-08-06，獨立於能力評分）

> 目的：MTP 是「速度」特性，不該跟能力分數混在一起。用同一個模型、同一道長文生成題（Q8，max_tokens=600，temp 0.6，thinking off），三種配置各跑 5 次。腳本：`tests/bench_mtp.py` + `tests/bench_mtp_driver.sh`。

**硬體**：RTX 5070 Ti 16GB。**判定標準（預設）**：MTP 速度 ≥ +10%、品質不降、無重複循環、acceptance 穩定 > ~50%。未達則用非 MTP。

| 配置 | gen tok/s（中位） | vs MTP 關閉 | TTFT ms | acceptance | 重複/斷句 |
|---|---|---|---|---|---|
| **MTP 關閉** | **58.49** | 基準 | 150 | — | 0/5、0/5 |
| MTP n-max=2 | 58.41 | −0.1%（≈持平） | 155 | 39%（36–45） | 0/5、0/5 |
| MTP n-max=4 | 45.73 | **−22%** | 154 | 23%（21–27） | 0/5、0/5 |

**判定結果**：
- ⛔ 速度 ≥ +10%：未過（n2 ≈ 持平，n4 反而慢 22%）
- ✅ 品質不降：過（三組輸出都連貫、守住全部設定、無重複，已人工抽查）
- ✅ 無重複循環：過
- ⛔ acceptance > 50%：未過（n2=39%、n4=23%）

**結論：未達標 → production 採用 MTP 關閉。** 根因是 acceptance 太低：這個模型的 MTP 草稿頭預測與實際生成分佈對不上，草稿常被否決；n-max=4 草擬越多被否決越多，算力白花反而更慢。已於 2026-08-06 將 `llm-chat.service` 的 `--spec-type draft-mtp --spec-draft-n-max 2` 移除。

## Thinking 開/關 A/B（2026-08-06，確認 thinking 到底有沒有用）

> 目的：production 模型可逐 request 控制 `enable_thinking`，所以用**更難的題**做 A/B——同一份 15 題（Q1–Q10 原題＋Q11–Q15 新增推理壓力測試），全關 vs 全開各跑一次，比對客觀通過率與 token 成本。腳本：`tests/test_model_eval.py`（加 `THINKING=on/off` 全域切換；開啟時 max_tokens ×3 上限 6000，避免思考鏈被截斷）。

新增的難題電池 Q11–Q15（皆 System-1 陷阱，附程式化檢查）：Q11 六任務六約束排程、Q12 漲20%再打八折、Q13 騎士與無賴真假話、Q14 蝸牛爬井終止條件、Q15 倉庫多步進出貨。

| | 通過 | 總 completion tokens |
|---|---|---|
| **THINKING=off** | **37 / 40** | **5,233** |
| **THINKING=on** | 36 / 40 | 30,222（**5.8 倍**） |

逐題（客觀檢查 通過/總數，括號為 completion_tokens）：

| # | OFF | ON | 備註 |
|---|---|---|---|
| Q1 指令遵循 | 4/5 (46) | 2/5 (2400) | ON `finish=length`：思考鏈吃光預算，答案被截斷 → 格式檢查失敗 |
| Q2 條件推理 | 2/2 | 2/2 | |
| Q3 找資訊不足 | 2/2 (322) | 2/2 (3000, length) | ON 截斷但檢查剛好過 |
| Q4 抵抗假資料 | 1/2 | 1/2 | 兩者其實都正確拒絕，1/2 是檢查詞表未認「未能確認」（已修正詞表，但此 run 用舊記錄） |
| Q5 數值推理 | 1/1 | 1/1 | |
| Q6 摘要 | 2/2 | 2/2 | |
| Q7 台灣語境 | 1/1 (35) | 1/1 (1500, length) | ON 截斷但剛好過 |
| Q8 創作 | 3/3 | 3/3 | |
| Q9 長上下文 | 4/4 | 4/4 | |
| Q10 自我檢查 | 2/3 | **3/3** | ON 唯一實質增益 |
| Q11 多約束排程 | 7/7 | 7/7 | OFF 這次也全對（前一次 run OFF 只 5/7，是 run variance，非穩定差異） |
| Q12 百分比陷阱 | 3/3 | 3/3 | 兩者都對 |
| Q13 真假話 | 2/2 | 2/2 | |
| Q14 蝸牛爬井 | 2/2 | 2/2 | |
| Q15 多步計算 | 1/1 | 1/1 | |

**結論：對這個模型，thinking 不值得開。**

1. **更貴又沒更好**：全開 30,222 tokens vs 全關 5,233 tokens（5.8 倍），通過率反而低 1 分（36 vs 37）。
2. **思考鏈會吃光預算**：ON 在 Q1/Q3/Q7 出現 `finish_reason=length`，答案被截斷（要嘛格式檢查失敗如 Q1，要嘛剛好擦邊過如 Q3/Q7）。要可靠就得再放大 max_tokens，成本更高。
3. **唯一增益只有 Q10 一題**，且幅度有限；難題電池（Q11–Q15）關閉就幾乎全對——這個模型在數學／真假話／終止條件／多步計算上，不開 thinking 就夠強。
4. **Q11 的「thinking 較強」是假象**：第一次 A/B OFF 只 5/7、ON 7/7，看似 thinking 贏；重跑後 OFF 也是 7/7，證實是模型非確定性的 run variance，單次 run 無法乾淨歸因給 thinking。

**落地建議**：production 維持預設 `--reasoning off`（已部署）；呼叫端預設不送 `enable_thinking:true`。逐 request 的開關仍保留，但本基準的證據不支持常規開啟——即使開，也要把 `max_tokens` 拉到非常大才不會截斷，代價不划算。

> 註：本次 A/B 為單次 run，受模型非確定性影響（temp 雖 0.3 仍有變異）。但「token 成本 5.8 倍」是確定的，且「思考鏈截斷風險」是系統性的，所以即便 best case 也只是平手、成本卻高數倍——結論方向穩健。
